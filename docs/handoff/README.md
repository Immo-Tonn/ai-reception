## 2. Что делает #26 (миграция 0033)
- Убрана политика `audit_logs_insert`; у `anon`/`authenticated` нет прав записи (только чтение по `audit_log.view`); `service_role` — только INSERT. UPDATE/DELETE невозможны.
- Запись аудита обычных сервисов — один серверный модуль `src/server/audit/` (единственный insert, проверяется тестом): пользователь определяется `auth.getUser()`, проверяется членство, `action`/`entityType` из фиксированных списков, `source` всегда `user`. Список файлов с service role расширен ровно на `src/server/audit/deps.ts`.
- Архив и срок хранения аудируются триггерами в той же транзакции (`set_client_archived`/`set_client_retention_months` больше не вставляют сами). Экспорт — узкая функция `record_client_export_audit` с флагом транзакции, который ставит только `export_client_data`.
- Остальные definer-функции, пишущие аудит (публичная запись, профиль, аккаунты, расписание, анонимизация, запросы субъектов), работают как раньше.
- EXECUTE отозван у явного списка из 32 триггерных функций приложения одним блоком; тест проверяет полноту списка, запрет прямого вызова и что API-функции не затронуты. Системные функции и расширения не тронуты.
- Ошибки записи аудита логируются кодом (без ПД, текста ошибки, id).
- **Известное ограничение (принято):** изменение и аудит обычных сервисов — два запроса; при сбое аудита изменение остаётся, ошибка логируется (не глотается молча). Атомарные операции аудируются в базе.
