## Общие ограничения (действуют на всех этапах)
- Не трогать работающий функционал: бронирование, календарь, Google Calendar, ICS (кроме отзыва при анонимизации), счета и отчёты, авторизацию, услуги, сотрудников, расписания, уведомления (кроме очистки), дизайн, навигацию, Vercel, Supabase и ENV, старые миграции. Никакого рефакторинга «заодно» и переименований. Новые зависимости — только при необходимости.
- Production: без отдельного согласования не применять миграции, не менять и не удалять реальные данные, не менять ENV, не включать автоматическую анонимизацию, не удалять счета и историю записей, не менять юридические тексты, не делать merge и деплой. Тесты — только на синтетических данных (PGlite, при необходимости локальный Supabase). Не копировать реальные ПД в тестовую базу.
- Git: небольшие PR, по возможности одно изменение схемы на PR. PR создаётся только после показа результата владельцу. Merge делает только владелец или по его явной команде.
- Каждый PR: релевантные тесты, изоляция организаций, права ролей, отсутствие ПД в логах, `npm run build`, проверка влияния на существующие функции. Ошибки вне задачи — сообщать, не исправлять.
- Экономия токенов: сначала Graphify и этот документ, затем точечный поиск. Без полного аудита, без параллельных агентов, без длинных логов. Короткий отчёт после этапа: что проверено, найдено, изменено, тесты, что осталось, риски.

## Согласованные решения
- Удаление аккаунтов Supabase Auth (`auth.users`, `client_accounts`) и ICS-токен аккаунта делает **другой разработчик**. Анонимизация клиента бизнеса **не является** полной анонимизацией человека с аккаунтом: это ограничение фиксируется в UI и документации.
- Метка обезличенного клиента: **`Gelöschter Kunde`** (без короткого ID). Внутренние ID сохраняются только для целостности истории.
- Анонимизирует **только owner** (право `clients.erase`). Проверка выполняется в базе, UI лишь скрывает кнопку.
- Клиент не удаляется физически: строка обезличивается через UPDATE (на неё ссылаются записи, счета и сделки; FK сделок `NO ACTION`).
- Срок хранения 36 месяцев — **предварительный**, не выдавать за требование GDPR. Автоудаление выключено (`AUTO_ANONYMIZE_ENABLED=false`).

После восстановления старого бэкапа service role вызывает `reapply_client_erasures(<строки ledger, сохранённые вне БД>)`. **Ограничение:** где хранить копию ledger вне базы — решение команды (не реализовано, описать в BACKUP_RECOVERY).

## Этап 2 — экспорт данных ⏳
- Серверный экспорт одного клиента: JSON (CSV при необходимости). Права: owner и admin. В каждом запросе проверять workspace_id и client_id.
- Состав: профиль, записи, счета, waiting_list, leads и quotes (и jobs/projects), связанный аккаунт клиента (если есть), прочие данные клиента.
- `internal_notes` автоматически не включать. Отдельная оценка оснований и подтверждение owner.
- Передача: защищённый ответ сервера, `Cache-Control: no-store`, без Storage и публичных ссылок, без ПД в логах.
- Журнал `data_subject_requests` с минимальными метаданными. Режимы: административный экспорт и подготовка ответа по Art. 15. Юридические тексты не писать.
- Проверка: изоляция A/B, роли, заголовки, отсутствие ПД в логах, build.

## Этап 3 — Cron и dry-run ⏳
- Расширить существующий `/api/cron/external-calendar-cleanup`, если это безопасно. `CRON_SECRET`, идемпотентность, независимые шаги, лимиты Vercel Hobby (1 раз в сутки), логи только со счётчиками.
- Очистка просроченных `booking_claims`. Dry-run уведомлений. Подсчёт кандидатов на анонимизацию с исключениями: будущие записи, незакрытые статусы, открытые счета и т. п.
- `AUTO_ANONYMIZE_ENABLED` выключен по умолчанию и не включается. Счета и записи с обязательным сроком хранения не удалять.
