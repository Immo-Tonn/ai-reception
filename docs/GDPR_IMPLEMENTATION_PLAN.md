## Общие ограничения (действуют на всех этапах)
- Не трогать работающий функционал: бронирование, календарь, Google Calendar, ICS (кроме отзыва при анонимизации), счета и отчёты, авторизацию, услуги, сотрудников, расписания, уведомления (кроме очистки), дизайн, навигацию, Vercel, Supabase и ENV, старые миграции. Никакого рефакторинга «заодно» и переименований. Новые зависимости — только при необходимости.
- Production: без отдельного согласования не применять миграции, не менять и не удалять реальные данные, не менять ENV, не включать автоматическую анонимизацию, не удалять счета и историю записей, не менять юридические тексты, не делать merge и деплой. Тесты — только на синтетических данных (PGlite, при необходимости локальный Supabase). Не копировать реальные ПД в тестовую базу.
- Git: небольшие PR, по возможности одно изменение схемы на PR. PR создаётся только после показа результата владельцу. Merge делает только владелец или по его явной команде.
- Каждый PR: релевантные тесты, изоляция организаций, права ролей, отсутствие ПД в логах, `npm run build`, проверка влияния на существующие функции. Ошибки вне задачи — сообщать, не исправлять.
- Экономия токенов: сначала Graphify и этот документ, затем точечный поиск. Без полного аудита, без параллельных агентов, без длинных логов. Короткий отчёт после этапа: что проверено, найдено, изменено, тесты, что осталось, риски.

## Согласованные решения
- Удаление аккаунтов Supabase Auth (`auth.users`, `client_accounts`) и ICS-токен аккаунта делает **другой разработчик**. Анонимизация клиента бизнеса **не является** полной анонимизацией человека с аккаунтом: это ограничение фиксируется в UI и документации.
- Метка обезличенного клиента: **`Gelöschter Kunde`** (без короткого ID). Внутренние ID сохраняются только для целостности истории.
- Анонимизирует **только owner** (право `clients.erase`). Проверка выполняется в базе, UI лишь скрывает кнопку.
- Клиент не удаляется физически: строка обезличивается через UPDATE (на неё ссылаются записи, счета и сделки; FK сделок `NO ACTION`).
- Срок хранения 36 месяцев — **предварительный**, не выдавать за требование GDPR. Автоудаление выключено (`AUTO_ANONYMIZE_ENABLED=false`).

## Этап 4 — настройки хранения ✅
- Срок хранения на уровне организации, предварительно 36 месяцев. Определить событие, от которого идёт отсчёт, включая клиентов без визитов.
- UI раздельно показывает: предварительную политику, выбранный срок, фактически работающие механизмы, статус автоочистки (выключена).
- Не создавать medical-профиль. Не выдавать срок за универсальное требование GDPR. Не включать автоудаление.

Реализация (ветка `feature/gdpr-retention-settings`, миграция `0031`; применять после `0028` → `0029` → `0030`):
- **Где хранится:** `workspaces.client_retention_months` (int, по умолчанию **36**, допустимо **12–120**, проверка в базе и на сервере). **Это предварительные технические границы, а не юридические требования** (Needs legal review): ни GDPR, ни § 147 AO такой диапазон не предписывают. Ориентиры: нижняя граница совпадает с предварительным сроком уведомлений (12 месяцев), верхняя взята по 10-летнему сроку хранения отдельных деловых документов (например, § 147 AO) лишь как точка отсчёта — это не означает, что клиентские данные нужно или можно хранить так долго.
- **Кто меняет:** только owner (право `retention.manage`). Политика UPDATE на `workspaces` разрешает owner и admin менять настройки (`settings.manage`), поэтому триггер `workspaces_guard_retention_setting` запрещает менять эту колонку всем без `retention.manage`, в том числе прямым запросом к API. Admin видит значение (read-only), manager, staff и accountant раздела не видят.
- **Интерфейс:** «Настройки → Хранение данных» — отдельно рекомендуемый срок (36, предварительно), выбранный срок и фактический статус («автоматическая анонимизация выключена»), пояснение, что сохранение ничего не удаляет.
- **Влияние на dry-run:** `0031` переопределяет `retention_dry_run` из `0030` с той же сигнатурой: срок теперь берётся у каждой организации (`now() - client_retention_months`), глобальное значение cron (36) — только запасное. В отчёте `clients.periodSource = 'workspace_setting'`. Код cron из PR #20 менять не нужно.
- **Почему автоочистка выключена:** сроки не согласованы юристом, автоматическая анонимизация не реализована, флаг `AUTO_ANONYMIZE_ENABLED` ничего не включает (этап 3).
- **Требует юридического согласования:** рекомендуемый срок 36 месяцев, границы 12–120, событие отсчёта (последний завершённый визит; клиенты без визитов — отдельная группа), сохранение имени в счетах (категория C).
- Тесты: `migration0031.test.ts` (9), `retentionSettings.test.ts` (3); совместная проверка с PR #18–#20.
