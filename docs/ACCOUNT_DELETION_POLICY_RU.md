# Удаление и анонимизация аккаунтов — предложение политики

> Перевод документа [ACCOUNT_DELETION_POLICY.md](ACCOUNT_DELETION_POLICY.md). При расхождениях основным считается английский текст.

**Статус: ПРЕДЛОЖЕНИЕ, требует одобрения команды.** Ничего из описанного здесь ещё не реализовано. Числа —
значения по умолчанию; в коде они хранятся как именованные константы, поэтому изменить их можно одной строкой.
Это не юридическая консультация: документ нужно проверить у юриста до того, как на платформе появятся настоящие
клиенты и настоящие счета.

## 1. Позиция продукта (нужно решение команды)

ServiceOS — инструмент для **онлайн-записи, управления записями и работой сотрудников и контроля за ними**.
Цены, платежи и счета в приложении служат для повседневного контроля самого бизнеса и для внутренней
статистики. ServiceOS **не является** официальной бухгалтерской системой бизнеса: законный бухгалтерский учёт
бизнес ведёт в собственной лицензированной программе. Если команда согласна, это нужно указать в Условиях
использования и в Datenschutz (политике конфиденциальности).

Следствие: персональные данные клиента не хранятся «ради налоговых обязанностей ServiceOS», поэтому запрос
клиента на удаление можно исполнить анонимизацией, не дожидаясь окончания какого-либо нашего срока хранения.

## 2. Клиент удаляет свой аккаунт

| Шаг | Когда | Что происходит |
|---|---|---|
| Запрос | Клиент подтверждает в личном кабинете (паролем или кодом из письма) | Выход из системы; будущие записи **отменяются** (бизнес видит «отменено клиентом»); аккаунт получает отметку «ожидает удаления» |
| Льготный период | `CLIENT_DELETION_GRACE_DAYS = 30` | Повторный вход отменяет запрос; больше ничего не теряется |
| Анонимизация | После льготного периода (задача по расписанию) | Логин и строка `client_accounts` удаляются; карточка клиента в **каждом** бизнесе, связанном с аккаунтом, анонимизируется (имя -> «Deleted client», email, телефон и заметки очищаются); снимки этого клиента во «Входящих» вычищаются (`forget_client_in_inbox`) |
| Сохраняется | Всегда | Сама запись (дата, услуга, сотрудник, статус, сумма) без привязки к человеку, чтобы календарь и собственная статистика бизнеса оставались согласованными |

Гость, который никогда не создавал аккаунт, пользуется тем же удалением через **запрос, подтверждённый кодом
из письма** (механизм одноразового кода, который уже используется для восстановления пароля).

## 3. Владелец удаляет бизнес

| Шаг | Когда | Что происходит |
|---|---|---|
| Запрос | Только владелец; вводит slug рабочего пространства; повторно вводит пароль | Бизнес становится недоступным (страница записи, каталог, вход сотрудников); владелец может его восстановить |
| Льготный период | `BUSINESS_DELETION_GRACE_DAYS = 30` | Данные хранятся без изменений |
| Удаление | После льготного периода (задача по расписанию) | Строка `workspaces` удаляется; всё остальное удаляется следом через `ON DELETE CASCADE` (записи, клиенты, услуги, сотрудники, счета, «Входящие», подключения календарей). Логин владельца остаётся |
| До удаления | По желанию, позже | Владелец может выгрузить клиентов и записи в файл |

Примечания: защита от удаления записей (0027) не блокирует каскадное удаление всего рабочего пространства;
выданный доступ к Google Календарю следует отозвать на стороне Google до удаления строки (отдельная задача);
резервные копии хранят удалённые данные, пока не истечёт срок самих копий (указать это в Datenschutz).

## 4. Техническая схема (без `service_role`)

- Каждая операция — это SQL-функция (`security definer`, зафиксированный `search_path`), которая действует
  только от имени `auth.uid()`; миграции применяются вручную после того, как команда согласует их номера.
- Нужна одна задача по расписанию для завершения льготного периода (Vercel Cron, как в ветке календаря).
- Логин, которому всё ещё принадлежит бизнес, удалить нельзя: сначала нужно удалить бизнес.

## 5. Журнал «Входящих» (события-«призраки»)

События «Входящих» — это снимки, которые триггер базы данных записывает при создании, переносе или отмене
записи. После удаления записи (оно разрешено для записей, созданных по ошибке) её события остаются, и в них
по-прежнему есть имя клиента — в поле `preview` и в снимке. Предложение:

1. При физическом удалении записи писать событие «запись удалена», чтобы журнал оставался честным.
2. По желанию — приглушать или скрывать события, запись которых больше не существует.
3. Срок хранения: старые события удаляются автоматически (PR #8 уже добавляет настройку срока хранения «Входящих»).
4. Анонимизация клиента также вычищает имя из `preview` и из снимка (`forget_client_in_inbox`).

Нужно согласовать с PR #8 (`booking-status-inbox-ux`), чтобы не дублировать работу.

## 6. Открытые вопросы

1. Льготные периоды: предлагается 30 дней (а не 6–24 месяца: долгий период «храним всё» трудно обосновать для
   данных, которыми никто не пользуется).
2. Окно восстановления после удаления бизнеса: те же 30 дней?
3. Выгрузка перед удалением: обязательна к запуску или позже?
4. Окончательные формулировки для Условий использования и Datenschutz (резервные копии, «не бухгалтерская система»).
